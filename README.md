# keby-landing

Лендинг Кэби — обычный статический сайт: HTML, CSS, JS, картинки и шрифты
лежат отдельными файлами. Выкладывается на **https://keby.clientbase.ru/**

## Бренд и адреса

Домен продукта — **keby.ai**. Его используем везде, где адрес наш собственный:
например, в макете браузера в секции «Интерфейс» показан `crm.keby.ai/...`.

`clientbase.ru` остаётся там, где адрес настоящий и подменять его нельзя:

- юридические документы (оферта, согласие на обработку данных);
- страница тарифов;
- почта `info@clientbase.ru` в подвале;
- обработчик регистрации и хост созданного аккаунта `<логин>.clientbase.ru`;
- `canonical` и Open Graph — лендинг сейчас выложен на `keby.clientbase.ru`.

Последний пункт поменяется, если лендинг переедет на свой домен.

## Как посмотреть локально

Просто открыть `index.html` в браузере не получится — браузер запрещает
локальной странице подгружать соседние файлы. Нужен любой локальный сервер,
например:

```
python3 -m http.server 8000
```

и открыть http://localhost:8000

## Как выложить

Сама страница статическая: никаких сборки и зависимостей не требуется —
React и шрифты лежат внутри репозитория. Наружу она ходит только за
счётчиком Яндекс.Метрики. Единственная серверная часть — `api/sms.php`
(подтверждение телефона), ей нужен PHP с `pdo_sqlite` и `curl`; в образе
`php:8.2-apache` всё это есть. Без настроенного конфига она просто выключена,
а форма работает без подтверждения.

## Выкладка

Сайт живёт в контейнере `php:8.2-apache`, репозиторий склонирован в
`/var/www/html`. Обновление запускает `/etc/cron.daily/update_site`
(`git reset --hard` + `git pull --ff-only` под `flock`), а дёргает его
`update.php` из корня сайта.

### Автоматически, после push в main

`.github/workflows/deploy.yml` вызывает тот же самый endpoint по HTTPS —
ничего нового он не делает, просто нажимает ту кнопку, которую раньше
нажимали руками. Срабатывает только на push в `main`; ветки разработки и
pull request'ы деплой не трогают. Запустить вручную можно кнопкой
**Run workflow** на вкладке Actions.

Нужны три секрета в **Settings → Secrets and variables → Actions**:

| Секрет | Значение |
|---|---|
| `DEPLOY_URL` | `https://keby.clientbase.ru/update.php` |
| `DEPLOY_USER` | логин Basic Auth из конфига nginx |
| `DEPLOY_PASSWORD` | пароль оттуда же |

Раннер GitHub приходит с чужого адреса, поэтому Basic Auth ему нужен —
доверенные IP действуют только для офиса. Если `DEPLOY_USER` или
`DEPLOY_PASSWORD` окажутся пустыми, workflow сходит без авторизации и
упадёт на `401` — то есть молча ничего не сломает.

Любой ответ не из диапазона `2xx` роняет job. Тело ответа печатается всегда,
в том числе при ошибке (`curl --fail-with-body`) — иначе в логе не было бы
видно, что именно сказал `update_site`.

Cron остаётся резервным механизмом, его никто не отменял.

### Вручную

```
https://keby.clientbase.ru/update.php
```

С офисных адресов nginx пускает без пароля, с остальных спрашивает
Basic Auth. Ответ `200` и `Site updated successfully` означают успех, `500`
и `Site update failed` — что `update_site` завершился с ошибкой; её текст
печатается следом. Последней строкой идёт `Deployed commit` — по нему видно,
что именно сейчас развёрнуто.

Своей проверки доступа в `update.php` нет: точку входа закрывает nginx.
Это ограничение — единственное, что её защищает.

## Регистрация

Форма (одинаковая вверху и внизу страницы) собирает описание задачи, email,
имя и телефон. Все поля обязательны, кнопка не сработает и пока не отмечено
согласие с офертой и обработкой персональных данных — как на clientbase.ru.

Имя и телефон уходят как `mcontact` и `mphone` — под этими именами их ждут
обработчики КБ, и прокси их уже пересылает, отдельной правки не потребовалось.
Когда заполнены email, телефон и имя разом, обработчик ставит аккаунту
`Подтверждён = Да` (`$full_contacts` → поле `f26172`).

Отправка идёт в обработчик Платформы КБ. Цепочка такая:

```
keby.clientbase.ru (лендинг)
  → POST clientbase.ru/client_register_fast.php     ← прокси, curl на манеж
      → manage.clientbase.ru/client_register*.php   ← там создаётся аккаунт
```

Манеж закрыт снаружи, поэтому браузер обращается к прокси на основном
домене, а тот уже переправляет запрос curl-ом. Отсюда два следствия:

- **CORS-заголовок должен ставить прокси.** Тот, что стоит в скрипте на
  манеже, до браузера не доходит: `curl` с `CURLOPT_RETURNTRANSFER`
  возвращает только тело, заголовки ответа отбрасываются.
- **Прокси пересылает не всё подряд, а перечисленный список полей.** Чтобы
  бриф доехал, `brief` должен быть в этом списке.

Что уходит с лендинга: `mconf_id`, `memail`, `mcontact`, `mphone`,
`referer` / `code` / `friend`
из cookie `referer_frm`, `partner_id`, `friend_id`, пять `utm_*` из адресной
строки, `utm_mark_title` из cookie `title_mark` и `brief`.

Что приходит в ответ: логин нового аккаунта в
`data.command.data.command.parameters.login`. После него вызывается цель
`freeaccount` и происходит переход на `<логин>.clientbase.ru/login.php`.
При `type: "fast"` сразу, при `"standard"` — через 30 секунд.

Отказы приходят простым текстом, а не JSON (`die("Error: ...")` и
`cb_die(...)` на манеже). Всё, что не разобралось как JSON, показывается
пользователю понятной фразой: превышен часовой лимит в три регистрации,
исчерпан суточный лимит, аккаунт уже существует.

Настройки — в начале класса `Component` в конце `index.html`:
`KB_ORIGIN`, `REGISTER_PATH`, `MCONF_ID`, `METRIKA_ID`, `GOAL`.
Адрес обработчика выбирается по домену: если лендинг окажется на самом
`clientbase.ru`, запрос станет внутренним и CORS перестанет применяться.

### Что нужно от прокси на clientbase.ru

`clientbase.ru/client_register_fast.php` — это переходник: он собирает поля
из `$_POST`, отправляет их curl-ом на манеж и печатает ответ. От него нужны
две вещи, которых сейчас нет:

1. **CORS-заголовок.** Без него браузер отбрасывает ответ, и регистрация с
   лендинга не работает вообще.
2. **`brief` в списке пересылаемых полей.** Список задан явно, и брифа в нём
   нет — значит до манежа он не доезжает, сколько бы мы его ни слали.

### Почему запрос уходит без cookie и без заголовка validateAcc

На сайте КБ форма шлёт заголовок `validateAcc` и ставит одноимённую печеньку.
Ни один из обработчиков на манеже их не читает — все работают только с
`$_REQUEST`, а прокси и подавно ничего такого не пересылает.

Плюс два ограничения браузера. Если прокси отдаёт
`Access-Control-Allow-Origin: *`, звёздочка несовместима с `credentials` —
куки отпадают. А нестандартный заголовок потребовал бы предварительного
`OPTIONS`, который прокси пришлось бы отдельно обрабатывать. Ни то, ни другое
не нужно, поэтому запрос идёт без них — обычный простой POST.

### Описание задачи

Бриф уходит параметром `brief` и должен записываться в поле `f14992`
таблицы 191. Для этого в обоих обработчиках нужна строка:

```php
$upd_arr['f14992'] = form_input($_REQUEST['brief']);  // client_register_fast.php
$ins_arr['f14992'] = form_input($_REQUEST['brief']);  // client_register.php
```

Пока этих строк нет, бриф доезжает до сервера и виден в
`/home/logs/log_client_register.log`, но в карточку аккаунта не попадает.

Длина брифа ограничена 1000 символами (`BRIEF_MAX`). Ограничение не
косметическое: когда на манеже нет свободного предсозданного аккаунта,
`client_register_fast.php` делает `header('Location: client_register.php?' .
http_build_query($_REQUEST))` — переносит все поля, включая бриф, в строку
запроса, и `curl` идёт по этому адресу (`CURLOPT_FOLLOWLOCATION`). Кириллица
в percent-encoding занимает шесть байт на букву, поэтому 1000 символов дают
около 6 КБ URL при обычном лимите nginx в 8 КБ. Если поднимать потолок, надо
поднимать и `large_client_header_buffers` на манеже.

## Подтверждение телефона по SMS

Как только в поле телефона набран российский мобильный номер, рядом появляется
кнопка «Подтвердить». Она отправляет код из шести цифр, ниже открывается поле
для него, после верного кода у номера появляется «✓ подтверждён», и только
тогда кнопка «Собрать мою CRM» пропустит форму. В обработчик регистрации
вместе с `mphone` уходит `phone_token` — подписанное свидетельство, что этот
номер был подтверждён (см. ниже).

Обработчик лежит здесь же, на лендинге: `api/sms.php`. Три запроса:

```
GET  api/sms.php?action=challenge         → талон на отправку
POST api/sms.php  action=send  phone=…    → код ушёл (или причина отказа)
POST api/sms.php  action=check phone=… code=… → phone_token
```

Шлюз тот же, что был на clientbase.ru — sms16.ru (Intis), XML API.

### Настройка на сервере

Все секреты — только в `/etc/keby/sms.php`, вне каталога сайта и вне
репозитория. Образец — `api/sms.config.example.php`. На сервере:

```
mkdir -p /etc/keby /var/lib/keby-sms
cp /var/www/html/api/sms.config.example.php /etc/keby/sms.php
chown www-data /var/lib/keby-sms && chmod 750 /var/lib/keby-sms
chown root:www-data /etc/keby/sms.php && chmod 640 /etc/keby/sms.php
openssl rand -hex 32     # → в поле secret
```

В конфиге заполнить:

| Поле | Что писать |
|---|---|
| `secret` | вывод `openssl rand -hex 32`; подписывает талоны, коды и `phone_token` |
| `sms.login` / `sms.password` | учётка Intis: `sms_cb` и **новый** пароль (его меняли; в репозиторий он не пишется) |
| `sms.sender`, `sms.text` | подпись отправителя и текст; `{code}` заменяется на код |
| `trusted_proxies` | адрес nginx с точки зрения контейнера — см. ниже |
| `office_ips`, `office_code` | с офисных адресов SMS не уходит, код всегда `office_code` — чтобы проверять форму без расхода баланса |
| `dry_run` | `true` — вообще не слать, всем выдавать `office_code`; для отладки |
| `limits` | переопределение лимитов из `api/_lib.php`, при желании |

Сайт в контейнере: `/etc/keby` и `/var/lib/keby-sms` должны переживать
пересоздание контейнера — либо примонтировать их с хоста, либо создать внутри
образа. Каталог сайта для этого не годится: его перезаписывает `git reset
--hard` при каждой выкладке.

**Про IP клиента.** Внутри контейнера `REMOTE_ADDR` — это адрес nginx, а не
посетителя. Настоящий адрес берётся из `X-Real-IP` / `X-Forwarded-For`, но
только если запрос пришёл с адреса из `trusted_proxies`; иначе любой мог бы
подставить чужой IP заголовком и обойти лимиты. Значит, две вещи должны
сойтись: nginx обязан передавать `proxy_set_header X-Real-IP $remote_addr;`,
а `trusted_proxies` — содержать его адрес (обычно docker-подсеть, в образце
уже перечислены `172.16.0.0/12`, `10.0.0.0/8`, `127.0.0.1`). Если это не
настроено, все посетители сольются в один IP, лимит «на IP» сработает на
первых же восьми SMS в час и форма перестанет подтверждать номера у всех —
это будет видно в журнале.

Проверить, что всё поднялось:

```
curl -s https://keby.clientbase.ru/api/sms.php?action=challenge
```

`{"ok":true,"challenge":"…"}` — работает; `{"ok":false,"error":"not_configured"}`
— конфиг не найден, пустой `secret` или `state_dir`.

Журнал — `/var/lib/keby-sms/sms.log`: каждая отправка, отказ, срабатывание
лимита и потолка. Номера в нём замаскированы (`7999***4567`).

### Почему старый механизм сливал баланс и что сделано иначе

Старые `send_code.php` / `check_code.php` с clientbase.ru принимали любой
запрос, в том числе `GET` с чужого сайта, не считали запросы ни по IP, ни в
сумме, подставляли телефон в XML без экранирования (можно было дописать
чужих абонентов в одно сообщение), а проверка кода не ограничивала число
попыток и не знала про срок жизни. Итого: скрипт можно было дёргать в цикле,
пока не кончится баланс. Новый обработчик стоит на нескольких слоях, каждый
из которых сам по себе обходим, но вместе они делают атаку бессмысленной:

1. **Только POST и только со своего домена.** `Origin`/`Referer` обязаны
   указывать на нас. Отсекает самый массовый способ — запуск через `<img>`,
   `<form>` или скрипт с чужого сайта.
2. **Только российские мобильные.** Номер приводится к `79XXXXXXXXX`, всё
   остальное — отказ. Нельзя гонять SMS на дорогие направления, а в XML
   значения ещё и экранируются.
3. **Талон (challenge).** Перед отправкой страница получает подписанный
   талон, привязанный к IP; его нельзя использовать раньше чем через
   несколько секунд и позже чем через полчаса. Без загрузки страницы и паузы
   SMS не запросить, скрипту приходится держать сессию, а не слать голые POST.
4. **Ловушка.** Скрытое поле `website`: заполнено — ответ «ок», SMS нет.
5. **Лимиты** — на номер (3/час, 5/сутки), на IP (8/час, 20/сутки) и **общий
   потолок** (60/час, 400/сутки). Последний — главный: сколько бы адресов и
   номеров ни было у атакующего, больше 400 SMS в сутки с лендинга не уйдёт.
   Лимиты считаются и списываются в одной транзакции SQLite, гонок нет.
6. **Код** живёт 5 минут, 5 попыток ввода, одноразовый, в базе только его
   HMAC. Перебор бесполезен; проверки тоже лимитированы по IP (30/час).
7. **`phone_token`** — `телефон.срок.HMAC`, действует 30 минут. Регистрация
   получает его вместе с телефоном, и обработчик может проверить, что номер
   действительно подтверждён (см. ниже). Иначе можно было бы подтвердить один
   номер, а в форму отправить другой.

Настройки лимитов — в `limits()` в `api/_lib.php`, любое значение
переопределяется в `/etc/keby/sms.php`. При атаке в журнале появятся строки
`ПОТОЛОК send_global` — это сигнал посмотреть, откуда идёт поток, и при
необходимости прикрыть адреса на nginx.

Если понадобится ещё слой — Яндекс SmartCaptcha перед `action=send`. Сейчас
она не ставилась сознательно: лимиты и так закрывают расход, а капча портит
конверсию.

### Где что лежит

Старые `send_code.php` / `check_code.php` жили в корне clientbase.ru, и сайт
ходил к ним через CORS. Новый обработчик живёт **на самом лендинге**
(`keby.clientbase.ru/api/sms.php`), в том же контейнере, что и страница.
Так проще и надёжнее: запрос свой же, CORS не нужен, проверка `Origin`
работает строго, а выкладывается всё одним `git pull`. На манеж и на
clientbase.ru для отправки SMS ничего добавлять не нужно.

Что нужно от других серверов — только пробросить и проверить `phone_token`:

```
лендинг  ── mphone + phone_token ──▶ clientbase.ru/client_register_fast.php (прокси)
                                        └─▶ manage.clientbase.ru/client_register_fast.php
                                              проверяет подпись, помечает аккаунт
```

### Прокси на clientbase.ru

В списке `CURLOPT_POSTFIELDS` добавить две строки — `brief` и `phone_token`
(прокси пересылает только перечисленное):

```php
'brief'       => $_POST['brief'],
'phone_token' => $_POST['phone_token'],
```

Обратите внимание: `CURLOPT_URL` у прокси сейчас указывает на
`manage.clientbase.ru/client_register.php`, а не на `client_register_fast.php`.
Правки, сделанные в `_fast` на манеже (бриф в `f14992`, отметка о телефоне),
через прокси не сработают, пока адрес не поменять на `client_register_fast.php`
— тот сам перекинет на `client_register.php`, если предсозданного аккаунта
нет (`CURLOPT_FOLLOWLOCATION` у прокси включён).

### Манеж: client_register_fast.php

Нужен тот же `secret`, что в `/etc/keby/sms.php` на лендинге. Хранить его
на манеже тоже вне репозитория и вне каталога сайта, например в
`/etc/keby/sms_secret` (одна строка, `chmod 640`, владелец www-data).

После `include 'client_common.php';` — функция проверки:

```php
// Подтверждение телефона по SMS на лендинге Кэби. phone_token = телефон.срок.HMAC,
// подписан тем же secret, что в /etc/keby/sms.php на лендинге.
function keby_phone_verified($phone, $token) {
    $secret = trim(@file_get_contents('/etc/keby/sms_secret'));
    $p = explode('.', (string)$token);
    if ($secret === '' || count($p) !== 3) return false;
    list($tPhone, $exp, $sig) = $p;
    $norm = preg_replace('/\D+/', '', (string)$phone);
    if (strlen($norm) === 10 && $norm[0] === '9') $norm = '7' . $norm;
    if (strlen($norm) === 11 && $norm[0] === '8') $norm = '7' . substr($norm, 1);
    return $tPhone === $norm && (int)$exp > time()
        && hash_equals(hash_hmac('sha256', "verified|$tPhone|$exp", $secret), $sig);
}
```

Рядом со строкой `$full_contacts = ...`:

```php
$phone_verified = keby_phone_verified($client_phone, $_REQUEST['phone_token'] ?? '');
```

И в блок `$upd_arr` для таблицы 191 (рядом с `f26172`) — отметку. Если для
этого заведено отдельное поле «Телефон подтверждён», пишем в него:

```php
$upd_arr['fNNNNN'] = $phone_verified ? 'Да' : 'Нет';
```

Существующее `f26172` («Подтверждён») трогать не стоит: оно ставится по
факту заполненных контактов и используется остальными формами, у которых
SMS нет — иначе они все разом станут «Нет».

Если нужно не только помечать, но и **не создавать** аккаунт без
подтверждения, лендинг может дополнительно слать признак источника, а манеж
для него отказывать: `die('Error: phone not verified')` — лендинг понимает
этот ответ и предложит подтвердить номер заново. Сейчас это не включено.

Формат телефона: лендинг шлёт `mphone` как `+79XXXXXXXXX`, в токене номер без
плюса — функция выше приводит оба к одному виду сама.

### Что стоит сделать вне репозитория

Учётные данные из старых скриптов (пароль Intis, ключ шифрования файла
кодов, ключ CarrotQuest) в переписке засветились — пароль Intis уже сменён,
остальное лучше тоже перевыпустить. Новый пароль хранится только в
`/etc/keby/sms.php`.

## Аналитика

Яндекс.Метрика, счётчик `19963723` — тот же, что на clientbase.ru. Цель
`freeaccount` вызывается перед переходом в созданный аккаунт, как в
`goto_new_acc()` на сайте КБ.

## Номер сборки

В подвале рядом с копирайтом стоит номер сборки — по нему видно, обновилась
ли выложенная версия. Значение задаётся полем `BUILD` в классе `Component`;
поднимайте его при каждой выкладке.

## Как устроена страница

Разметка внутри `<x-dc>` — это шаблон с подстановками `{{ ... }}`,
условиями `<sc-if>` и циклами `<sc-for>`. Данные и обработчики для него
задаёт класс в блоке `<script type="text/x-dc">` в конце `index.html`.
Отрисовывает всё это `assets/js/dc-runtime.js`.

Этот блок со скриптом должен оставаться внутри `index.html` — рантайм читает
его содержимое напрямую и не умеет подключать по `src`.
